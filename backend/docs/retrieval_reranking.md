# RepoSage Phase 3G: Retrieval Reranking

## Overview

RepoSage implements retrieval reranking to improve the final ranking precision of context-aware code chunks. 

The retrieval architecture follows a pipeline:
1. **Candidate Generation**: Qdrant (Semantic Search) and BM25 (Keyword Search) each retrieve an initial candidate pool (e.g. `semantic_candidate_k = 50`, `keyword_candidate_k = 50`).
2. **Fusion**: Reciprocal Rank Fusion (RRF) interleaves these results into a single candidate pool.
3. **Reranking (Phase 3G)**: The top `reranker_candidate_k` (e.g., 30) chunks from RRF are passed to a `RerankerProvider`.
4. **Final Top-K**: The provider reranks the candidate pool, and the top `top_k` (e.g., 10) are returned to the API client.

## Why Reranking?

RRF provides robust candidate generation but lacks deep semantic alignment between the query and the text. A reranker (such as a CrossEncoder) can compare the query to the exact Phase 3F context-aware document representation (`File`, `Language`, `Module`, `Class`, `Parent`, `Symbol`, `Context`, `Type`, `Code`) to produce highly precise rankings that bi-encoder embeddings and BM25 miss.

## Configuration

Reranking is strictly opt-in. Configuration is driven via `app/core/config.py` (or `.env`):

```env
RERANKER_ENABLED=false
RERANKER_PROVIDER=mock
RERANKER_MODEL=""
RERANKER_CANDIDATE_K=30
```

### Parameter Semantics
- `semantic_candidate_k`: Chunks retrieved from Qdrant.
- `keyword_candidate_k`: Chunks retrieved from BM25.
- `reranker_candidate_k`: Chunks sent from the RRF pool to the reranker.
- `top_k` (API request): The final number of chunks returned to the client.

**Reranking only happens when `mode=hybrid` and `RERANKER_ENABLED=true`.**

## Score Preservation and Observability

The reranker MUST NOT overwrite existing scores. The API response for a chunk will include:
- `rrf_score`: Original RRF score
- `semantic_rank`: Original position in semantic search
- `keyword_rank`: Original position in keyword search
- `reranker_score`: The new score generated by the reranker provider
- `rank`: The final position in the returned list

When `debug=true` in the request, the response payload will also include:
- `reranker_latency_ms`: Time taken by the provider to rerank the candidates
- `candidate_count`: Number of candidates evaluated

## Graceful Degradation

If the configured reranker provider throws an exception, the `SearchService` will:
1. Log the failure (including `repository_id`, `candidate_count`, `error_type`).
2. **Gracefully fallback** to returning the original RRF candidates truncated to `top_k`.
3. Set `reranker_score` to `None`.

The API request will **not** return a 500 Internal Server Error.

## Provider Abstraction

Reranking providers must implement the `RerankerProvider` abstraction in `app/modules/retrieval/reranker.py`:

```python
async def rerank(
    self, query: str, candidates: list[RerankerCandidate], top_k: int
) -> list[RerankerCandidate]:
```

### MockRerankerProvider (Pipeline Validation)

Currently, the default provider is `MockRerankerProvider`. 

> [!WARNING]
> **MockRerankerProvider is a deterministic test provider and must not be interpreted as evidence of production retrieval-quality improvement.**
> It uses deterministic lexical overlap against structural fields (`context_path`, `symbol_name`, `class_name`) to verify the orchestration pipeline, fallback behavior, and score preservation.

## Future Real Reranker

In the future, a true `CrossEncoderRerankerProvider` (e.g. using `sentence-transformers`) can be added by implementing the abstraction and setting `RERANKER_PROVIDER=cross_encoder`. The SearchService orchestration is already designed to handle this seamlessly without architectural changes.
